# Product TODO: Career Journey

Future user-facing direction: evolve the Improvements concept toward **Career Journey**.
Documentation only: no UI implementation or route rename in this slice.

- NOW -> NEXT -> LATER
- Maintain / Improve / Build / Explore
- Quests and a weekly direction checkpoint
- Learning -> practicing -> proven -> strength
- Growth timeline and possible paths
- Future paths unlocked by current paths

Human agency remains primary. Source repair is not a learning quest: an existing record with
broken provenance should be repaired before asking the candidate to supply the experience again.
No generated checkpoint may self-confirm proof or prescribe learning from missing provenance.

## Purpose

Make professional growth visible enough that the user knows what to maintain,
what to build next, and why it matters. WorkPilot must not define the user's career.

## NOW

Current position, proven strengths, current direction and what to maintain.

## NEXT

Two to four active quests: improve/build through study, practice and evidence.
Keep user objectives visible and offer a future weekly goals/direction check-in.

## LATER

Possible paths, structural distances and paths that unlock future paths.
These are options for the user, not algorithmic career prescriptions.

## Progress and timeline

LEARNING -> PRACTICING -> PROVEN -> STRENGTH.
The timeline emphasizes learning/evolution, not LinkedIn-style employer chronology:
started learning, practiced, added evidence, capability strengthened, new path became
plausible, target changed, role obtained, new future paths opened.

## Recursive loop

Career Memory -> Candidate Profile -> Profile Checkpoint -> Career Journey -> user action
-> learning/practice/evidence/outcome -> confirmed Career Memory update -> Candidate Profile vN+1
-> new checkpoint -> another user-directed iteration.

Transferable support remains adjacent when direct prior ownership is required. An unsatisfied
direct constraint is not a command to invent evidence; an explicit absence should not trigger
repetitive evidence requests. Keep learning, provenance repair and proof collection distinct.

## Temporal refresh, not starting from zero

Relevant historical evidence may remain valid while an explicit CURRENT_REQUIRED constraint is
NOT_SATISFIED. Future UI should offer UPDATE / REFRESH, for example "Refresh current regulatory
procedure knowledge", not "Learn regulatory procedures". Historical proof is not erased or turned
into GAP/EVIDENCE_MISSING. UNKNOWN applicability invites clarification, not an assumed deficiency.
Use the structured temporal requirement and applicability carried by HowToProve; no UI is added here.
